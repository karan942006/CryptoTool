7. HOW IT DISCOVERS CRYPTOGRAPHY & ALGORITHMS (STATIC ANALYSIS EXPLAINED SIMPLY)
================================================================================
Judges often ask: "How does your scanner actually find the algorithms in code?"

Here is the simple, non-confusing explanation:

Method 1: Abstract Syntax Tree (AST) Tokenization
- Code is not just raw text; it has a structured grammatical tree.
- The scanner converts code into an Abstract Syntax Tree.
- It identifies:
  * Object instantiation (e.g., `new SecretKeySpec(...)`)
  * Method invocations (e.g., `Cipher.getInstance(...)`, `hashlib.sha256(...)`)
  * Parameter passing (e.g., inspecting what string was passed into `getInstance`)

Method 2: Multi-Pass Heuristic & Context Inspection
- If an algorithm name is stored in a variable, the scanner inspects assignment
  statements in that file to trace where the variable received its value.
- For key sizes, it scans a window of code around the cipher initialization to find
  key generator parameters (like `56`, `64`, `128`, `256`, `1024`, `2048`, `4096`).

Method 3: Live Network Handshake Simulation (TLS Auditor)
- For web servers, the scanner initiates a standard SSL/TLS `ClientHello` handshake.
- It doesn't send any attacks or exploits.
- It politely asks the server: "Which TLS version and cipher suites do you support?"
- The server responds with its active certificate, cipher suite (e.g.,
  `TLS_AES_256_GCM_SHA384`), and public key algorithm.
- The inspector checks if the certificate is expired, self-signed, or using weak SHA-1.

Method 4: Shannon Entropy Analysis
- Plain English text or code has predictable letter frequencies (entropy around 3.5 to 4.5).
- Truly random cryptographic keys or encrypted strings have maximum randomness
  (entropy above 7.2 out of 8.0).
- The scanner uses the Shannon Entropy mathematical formula:
    H = - Sum( P(i) * log2( P(i) ) )
  If a variable contains a high-entropy string, CryptoTool flags it as a suspected
  hardcoded private key or secret.

an application uses RSA, but it cannot differentiate between RSA-1024 (which is broken)

cannot generate a standardized CycloneDX v1.6 Crypto-BOM, has zero post-quantum

specialized Cryptographic Posture Management platform that bridges static source code
and live infrastructure into a unified quantum-risk dashboard."

ANSWER:

We also support hybrid deployment recommendations (e.g., X25519 + ML-KEM-768),
which NIST and IETF recommend during the transition period."

QUESTION 6: "What happens if a developer dynamically constructs an algorithm string at runtime (e.g., `algo = 'A' + 'ES'`)?"
ANSWER:
"We handle this through a dual-engine architecture:
1. Static AST constant propagation and expression evaluation that resolves basic
   string concatenations.
2. Fallback Heuristics: If an invocation like `Cipher.getInstance(var)` uses an
   unresolved variable, CryptoTool flags it as an 'Unresolved Dynamic Cryptographic
   Invocation'. In high-assurance security audits, unverified dynamic crypto is
   itself a code smell that requires human review."

QUESTION 7: "What is a Crypto-BOM and why does an organization need it?"
ANSWER:
"A Crypto-BOM (Cryptographic Bill of Materials) is a structured, machine-readable
inventory of all cryptographic assets—including algorithms, modes, key lengths,
curves, certificates, and libraries. Under White House NSM-10, India's National
Quantum Mission guidelines, and the European Union's Cyber Resilience Act,
enterprises are required to maintain an active inventory of quantum-vulnerable
assets. CryptoTool generates this automatically in the global standard CycloneDX v1.6
format with a single click."

QUESTION 8: "Can your tool run in an air-gapped defense environment?"
ANSWER:
"Yes, 100%. The entire CryptoTool stack—the React frontend, Node.js API, Python AST
scanner, and PostgreSQL database—is fully containerized via Docker. It requires no
external cloud connection or third-party license servers. For defense agencies like
NTRO or military branches, it operates completely within air-gapped secure facilities."
